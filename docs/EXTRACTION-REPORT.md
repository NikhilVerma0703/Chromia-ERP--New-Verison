## 3. Database

`prisma/schema.prisma` holds 4 groups of blocks copied from the ERP schema. `prisma/migrations/0001_init/migration.sql` (generated by `prisma migrate diff --from-empty`) creates **47 tables and 21 enum types**:

1. **Chromia module**: 33 tables `chromia_*`, 19 enums. The schema is unchanged, and none of these tables link to tables outside Chromia.
2. **Attendance**: `attendance_operator`, `attendance_day`, `attendance_leave`.
3. **Finished-goods slice** (for Slab Intake and the inventory bridge): `fg_finished_slab`, `fg_slab_event`, `fg_design_alias`, `design_name`, `fg_sales_approved_batch`, `fg_sales_hidden_design`, `entry_photo`, `commercial_design_code`; enums `SlabStatus`, `SlabSource`.
4. **Production-line lookups** (read-only; Slab Intake prefill): `polish_qc`, `press`, `jot`.

Not reproduced: partial and expression indexes the ERP created by hand on Neon (they are not in its Prisma schema either), and Neon-only backup tables.

Seeds: `prisma/seed-chromia.ts` (master data) and `prisma/seed-attendance.ts` (operator roster), both unchanged.

## 6. Known gaps, findings and dependencies still on the main ERP

1. **Change-request documents (Aug–Sep 2026) are still missing.** The three `.mbox` patch series supplied on 27 Oct (18–26 Oct 2026) were checked against the code. Every Chromia/attendance change in them is present in the main ERP and therefore here; the analysis is in the session conversation. `docs/change-requests/` is ready for the August–September documents.
2. **Server time zone. Found, then resolved on 27 Oct at the owner's request.** Dates are stored as **midnight in the server's time zone**. Production runs on Vercel in **UTC**, but this PC runs on **Asia/Kolkata**, so at first a slab dated 20 Oct was stored as 19 Oct 18:30 UTC, and Import → Preview printed the day before. Now `dev`, `build`, `start` and the three seed scripts run with `TZ=UTC` (through `cross-env`, a dev dependency, because npm runs scripts in `cmd.exe` on Windows).

   Checked after the change, on a fresh test database (`chromia_erp_utc`):
   - Operator Entry stores 27 Oct as `2026-10-27 00:00` UTC, as production does.
   - Import Preview shows the register's own date.
   - Slab Records and the Dashboard's "today" figures still read in plant time.
   - The attendance "not later than now" rule still uses the plant clock: it accepted 06:00 and refused 23:30 at 10:28 plant time.

   The tests pass in both time zones. **No application code was changed.** Running `next dev` directly, without the npm script, falls back to the PC's time zone.
3. **Dev-only React warning (pre-existing).** "Two children with the same key" appears in the browser console right after some saves (QC, dispatch), naming the slab just saved. The code is byte-identical to the main ERP; nothing is shown wrongly.
4. **Finished goods is a local copy.** Slab Intake and the CHROMIA mark use this app's own `fg_*` tables (empty at first), not the production inventory. The inventory screens, sales holds, packing and dispatch stay in the main ERP.
5. **Slab Intake cannot add a slab until `design_name` has rows.** The save accepts only listed design names. That list is production master data, not seeded here.
6. **Attendance is not shared with the Robo line.** This is Chromia's own copy of the register.
7. **Slab Intake prefill** reads `polish_qc`, `press` and `jot`, which are empty unless production data is loaded.
8. **Left out with their modules:** the Finished Goods page (`/inventory`), Month Incentive, the daily attendance email, the ERP's global Undo.
9. **No real user attribution.** Every action is recorded as the local user.
10. **Seeds load `.env` themselves** (`tsx --env-file=.env`) and run with `TZ=UTC`. In the ERP, `DATABASE_URL` came from the shell.
